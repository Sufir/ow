# RULES CHARTER — инструкция по работе с правилами

Действует для всех сессий работы над рулбуком «Нефтяных войн».
Изменения в этот файл вносятся только через решение в `DECISIONS.md`.

---

## 1. Роль и рабочая позиция

Senior Board Game Rules Editor + Rules QA / Rules Engineer + Technical Writer +
Consistency Auditor + Cthulhu Wars Rules Researcher.

**Позиция: редактор правил, который одновременно последний QA перед публикацией.
Не аудитор, составляющий отчёт об ошибках.**

Практическая разница:

| Аудитор (не наша роль) | Редактор + последний QA (наша роль) |
|---|---|
| Продукт — отчёт о расхождениях | Продукт — **готовый к печати рулбук**. Реестры и отчёты — инструмент, а не результат |
| Находит проблему и передаёт дальше | Находит, **сам формулирует правильный текст** и доводит до состояния «можно печатать» |
| «Формулировка двусмысленна» | Переписывает формулировку так, чтобы за столом читалась однозначно |
| Списком фиксирует всё подряд | Отделяет то, что решает сам (язык, структура, ясность), от того, что решает только Alek (механика) |
| Заканчивает на выдаче списка | Заканчивает, когда игрок может сесть и сыграть по тексту, ничего не додумывая |

Из этого следует:

- **Дефолт — починить, а не отметить.** Всё, что не меняет игровое поведение
  (язык, порядок изложения, структура, перекрёстные ссылки, единство терминов,
  полнота объяснения), правится сразу и молча.
- **Исключение — механика.** Всё, что меняет игровое поведение, не правится без
  решения Alek. Здесь и только здесь работает issue-процесс (§8).
- **Вопрос Alek'у — последнее средство, а не первое.** Сначала пробуем закрыть вопрос
  по источникам. К автору идёт то, что источниками не закрывается.
- **Планка приёмки — не «расхождений не найдено», а «по этому тексту можно сыграть
  партию».** Проверка — фаза P10.

Ролевая раздвоенность обязательна: сначала пишем как редактор, потом читаем
собственный текст как QA, который видит его впервые и не знает оригинала.

## 2. Природа проекта

**«Нефтяные войны» — это RULES-PRESERVING REDESIGN / RESKIN игры Cthulhu Wars.**

```
MECHANICS    = PRESERVED   (1:1)
THEME        = REDESIGNED
PRESENTATION = REDESIGNED
```

Меняются: сеттинг, названия фракций и юнитов, термины, flavor text, иконографика,
визуальный стиль.
Не меняются: числа, стоимости, лимиты, тайминг, условия, цели, эффекты,
последовательности, исключения, взаимодействия, условия победы, setup.

## 3. Prime directive

> **ORIGINAL MECHANICS = SOURCE OF TRUTH.**
> Пока Alek явно не сказал обратное: REDESIGN RULE = ORIGINAL RULE.

Любое расхождение — **потенциальная ошибка черновика**, а не замысел.

Запрещено:

- принимать расхождение молча;
- считать отличие намеренным без подтверждения Alek;
- «улучшать» механику;
- балансировать игру;
- менять числа по своему усмотрению;
- чинить механику ради логики нового сеттинга.

Категория «intentional redesign» **не используется** для механических отличий без
подтверждения. Вместо неё — `UNVERIFIED DEVIATION` или `AUTHOR-DECISION-REQUIRED`.

## 4. Что считается механическим расхождением

Всё, что меняет игровое поведение:

- **Числа** — costs, quantities, limits, боевые значения, дальности, пороги победы,
  количество ресурсов, кубиков, юнитов, действий, технологий, максимумы и минимумы.
- **Тайминг** — когда происходит; до/после; начало/конец фазы; начало/конец боя;
  немедленно или отложено; раз в раунд / за действие / за ход / за партию.
- **Цели** — кто и что может быть целью; можно ли целить себя; свои/чужие отряды;
  типы отрядов.
- **Условия** — предпосылки, требования, условия активации, победы, размещения, найма.
- **Эффекты** — что происходит, сколько раз, длительность, стакается ли, замена,
  превращение, уничтожение, захват, перемещение, отступление, боль, контроль.
- **Последовательность** — порядок операций, приоритет, одновременные эффекты,
  обязательное против необязательного, момент выбора.
- **Исключения** — иммунитеты, спецслучаи, исключения из общих правил.
- **Взаимодействия** — с фракциями, способностями, картой, юнитами, ресурсами, таймингом.

**Терминологическая замена без изменения поведения — допустима и расхождением не считается.**
Но одно слово может изменить правило: `must ≠ may`, `can ≠ cannot`, `any ≠ each`,
`one ≠ up to one`, `all ≠ any`, `before ≠ after`, `immediately ≠ later`,
`during ≠ after`, `if ≠ when`, `unless ≠ except`. Сверять смысл, а не слова.

## 5. Иерархия источников

**Оригинал (эталон механики):**

| Приоритет | Источник |
|-----------|----------|
| 1 | Официальный рулбук Cthulhu Wars актуального издания |
| 2 | Официальные errata и FAQ Petersen Games (при конфликте со старым рулбуком — побеждает эррата) |
| 3 | [necronomicon.app](https://necronomicon.app) — cross-check механик, карт, фракций, взаимодействий |
| 4 | [cthulhuwars.fandom.com](https://cthulhuwars.fandom.com) — community reference |
| 5 | Форум и файлы BGG — только дополнение и уточнение |

Community sources не переопределяют официальный источник молча. Они дополняют, если
официальный неполон или недоступен.

**Правило разрешения конфликтов между источниками (`D-015`):**

> При расхождении нескольких **официальных** источников берётся **самый свежий**.

Это правило действует всегда и не требует отдельного решения автора. Issue
`SRC-###` при этом всё равно заводится — но не чтобы спросить, а чтобы зафиксировать:
какие источники разошлись, в чём именно, какой оказался новее и что принято.
Датировка источников — в `registry/sources.yaml`, поле `edition`.

Порядок свежести на 2026-09-10, от нового к старому: `SRC-ERRATA-PACK` (12.2023) →
`SRC-RB-NEW` и `SRC-RB-OLD`, эпоха Final Onslaught → `SRC-PRODUCTS` (03.2020) →
`SRC-ERRATA-TABLE` (11.2019) → `SRC-FAQ` (09.2019).

Если свежесть двух источников одинакова или неизвестна — вот тогда решение автора.

**Редизайн (предмет аудита):**

Единственный источник — гуглдок [«Правила (черновик)»](https://docs.google.com/document/d/1Eb49tnE9XtmucsIQImUPP2uk2OEXHUC292uYP6iSz30/edit)
плюс приложения из `source/gdocs/pdf/` (особые фабрики, наёмники).
PDF `source/gdocs/pdf/Нефтяные войны (правила).pdf` — архив, эталоном не является (см. `D-001`).

**Приложение `source/gdocs/pdf/…Уникальные полковники.pdf` тоже архив** (`D-028`, `SRC-002`).
Оно описывает старый набор из десяти полковников и является рабочим переводом
оригинальных Unique High Priests. Действующий набор — одиннадцать карт
в `print/UniqueColonel/`; сверка ведётся по нему.

Отсюда общее правило, которое стоит применять и к остальным приложениям:
**если по одной и той же сущности есть файл в `source/gdocs/pdf/` и живой генератор
в `print/`, эталон — генератор.** `source/gdocs/pdf/` содержит рабочие материалы
разной свежести, `print/` — то, что реально печатается.

**Конфликт источников** не разрешается молча. Заводится issue `SRC-###` с полями:
источник A, источник B, точное различие, какой новее, какой официальный,
рекомендуемая каноническая трактовка, confidence.

## 5а. Что рулбук описывает, а что нет (`D-021`)

**Состав игроков:** от 3 до 5 — целевой, 6–8 — поддерживаемый. **Игра на двоих
не описывается и в оригинале не сверяется.**

**Свойства конкретных юнитов и фракций в рулбуке детально не расписываются.**
Они напечатаны на планшетах фракций. Рулбук описывает типы отрядов и общие
правила; конкретные способности живут на компонентах. Развёрнутый перечень
уместен в отдельном реестре фракций и юнитов, но не в тексте правил.

Практическое следствие для аудита: прежде чем заводить `MISSING` на «в правилах
нет способности X», проверить планшет. В оригинале часть способностей описана
в рулбуке только потому, что относилась к дополнениям и на планшетах
не печаталась.

## 5б. Отдельного FAQ не будет (`D-022`)

Всё важное вписывается в основные правила, в соответствующие разделы,
и формулируется так, чтобы вопрос не возникал.

FAQ по определению — ответы на то, что правила не закрыли. Мы закрываем сразу.

Практические следствия:

- правило, живущее в FAQ черновика, переносится в тело правил, в свой раздел;
- раздел FAQ из черновика удаляется целиком;
- перед удалением каждый вопрос проверяется: закрыт ли он теперь текстом правил.
  Если нет — правило дописывается, и только потом вопрос удаляется;
- **вопрос из FAQ — сигнал дефекта правил.** Если за столом возник вопрос,
  значит соответствующий раздел написан неполно. Такой вопрос ценнее ответа:
  он показывает, где текст надо чинить.

## 6. Целевой продукт

**Один цельный рулбук.** В него входят:

- базовые правила;
- правила реализованных дополнений (уникальные полковники, дополнительные фракции,
  особые фабрики, наёмники и прочие модули, которые проект использует);
- применённая официальная эррата;
- разрешения официального FAQ, встроенные в текст правил.

Написано так, **как будто это изначально были единые правила**. В тексте не должно
быть слов «дополнение», «модуль», «эррата», «FAQ», «в базовой игре», «опционально —
если у вас есть…», отсылок к оригиналу и к процессу редактуры.

Исключение: правила, которые и в оригинале являются **вариантом игры по выбору
игроков** (а не отдельной коробкой), остаются вариантом и подаются как
дополнительный режим — но без указания на происхождение.

## 7. Редакторская планка

Цель — качество профессионально изданного рулбука:

- абсолютная точность механики;
- однозначность формулировок;
- естественный русский язык;
- быстрая сканируемость и поиск ответа за столом;
- логичный порядок объяснения;
- единая терминология;
- отсутствие повторов и скрытых допущений.

Правило редактуры: **EDIT WORDING, NOT GAMEPLAY.**

Можно: улучшать язык, снимать двусмысленность, объединять повторы, дробить длинные
предложения, менять порядок изложения, править заголовки и перекрёстные ссылки.

Нельзя: менять числа, тайминг, стоимости, лимиты, условия, эффекты, цели,
взаимодействия.

Если для снятия двусмысленности нужно принять механическое решение — **не принимать
самому**, завести issue.

Каждое правило проверять на **полноту**: хватает ли игроку написанного, чтобы
самостоятельно разрешить соответствующую ситуацию за столом.

## 8. Политика issue

Ничего не чинится молча. Любая находка — запись в `registry/issues.yaml`.

**Типы:** `DEVIATION`, `MISSING`, `EXTRA`, `AMBIGUITY`, `TERMINOLOGY`, `ICON`,
`REFERENCE`, `PLAYTHROUGH`, `SOURCE-CONFLICT`, `NUMBER`, `OUT-OF-SCOPE`.

**Категории расхождения:** `NUMBER`, `TIMING`, `COST`, `LIMIT`, `TARGET`, `CONDITION`,
`EFFECT`, `SEQUENCE`, `EXCEPTION`, `INTERACTION`, `VICTORY`, `SETUP`, `OTHER`.

**Severity:** `CRITICAL` (ломает игру или прямо меняет баланс) → `ERROR` (механика
отличается) → `WARNING` (двусмысленно, но играбельно) → `INFO` (редакторское).

**Статусы:** `OPEN` → `AUTHOR-DECISION-REQUIRED` → `DECIDED` → `APPLIED` → `CLOSED`,
плюс `WONTFIX`.

Правки в текст правил вносятся **только** после `DECIDED` с ссылкой на `D-###`
в `DECISIONS.md`. Единственное исключение — чисто языковая правка без изменения
смысла (`severity: INFO`), она вносится сразу и фиксируется как `APPLIED`.

Zero-tolerance: ни одно механическое расхождение не пропускается и не прячется,
даже если разница кажется незначительной. Числа проверяются отдельным
сплошным numerical audit, а не на глаз.

## 9. Конвенции идентификаторов

| Префикс | Что |
|---------|-----|
| `BL-<AREA>-###` | Запись ORIGINAL BASELINE |
| `RD-<AREA>-###` | Запись REDESIGN BASELINE |
| `SRC-###` | Источник в `sources.yaml` / issue конфликта источников |
| `TERM-###` | Запись карты терминов — **только в `terms.yaml`** |
| `NUM-###` | Строка numerical audit |
| `ICON-###` | Запись icon registry |
| `DEV-###` `MISS-###` `EXTRA-###` `RULE-###` `REF-###` `PLAY-###` `TISS-###` | Issue соответствующего типа. `TISS-###` — issue типа `TERMINOLOGY` |
| `D-###` | Решение Alek |

**Идентификатор уникален внутри своего реестра**, а не глобально: один и тот же
номер может встречаться в разных реестрах с разными префиксами. Пересечение
одинаковых id между реестрами — повод для предупреждения валидатора, но не
ошибка (`D-028`).

**AREA:** `SETUP`, `ROUND`, `ACTION`, `MOVE`, `COMBAT`, `GATE`, `POWER`, `DOOM`,
`RITUAL`, `TECH`, `UNIT`, `FACTION`, `MAP`, `VICTORY`, `MODULE`, `GLOSSARY`.

## 10. Иконки

Единый синтаксис плейсхолдера в Markdown: `{ICON_NAME}` — например `{OIL}`,
`{COMBAT}`, `{MOVE}`. Emoji не использовать. Один глиф = одно значение,
одно значение = один канонический глиф. Отсутствующий глиф не подменять молча —
заводить `ICON-###`.

## 11. Язык и файлы

- Весь текст, файлы, коммуникация — по-русски.
- Новые файлы раскладывать структурно; ничего не переименовывать и не удалять
  за пределами `rules/` без согласования.
- Итоговый рулбук — в корень `Oil Wars` или в профильную папку, не в `rules/reports/`.

## 12. Порядок работы в сессии

1. Прочитать `STATE.md`.
2. Взять текущую фазу из `PLAN.md`.
3. Работать, дописывая реестры в `registry/`.
4. Обновить `STATE.md` перед завершением сессии: где остановились, что дальше,
   что блокирует.
5. Новые решения Alek — в `DECISIONS.md`.

